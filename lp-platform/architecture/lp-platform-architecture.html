L&P Platform Architecture

The target design: what each part is, where it runs, and how the parts work together. It is derived from the platform requirements (Reference sheet) and your platform choices. The existing CIP repository is treated as a reference only; whether to reuse it or rebuild is a separate decision.

What you are building

Category, name and platforms

Standard description

An internal business development (BD) lifecycle platform for a security services contractor: capture, proposal and pricing management; win/loss and competitive intelligence; sales prospecting; client success; and contract administration after award.

Technically: a modular monolith web app; one operational system of record; containerized workers on Google Cloud for documents, crawling, connectors and solvers; a human-verified document pipeline; an analytics warehouse on BigQuery; and one remote MCP server so ChatGPT and Claude work with the same tools and permissions as staff.

Design rules

Nine rules that keep the pieces consistent

Every component and every future change gets checked against these. If two parts of the design ever disagree, these rules decide which one wins.

One operational system of record

Supabase Postgres + Storage hold live business data and original files. BigQuery is an analytical copy; Drive, Docs and Sheets are sources or outputs. Nothing else is a second truth.

One business-logic layer

The UI, MCP tools, workflows and jobs all call the same domain services. A rule is written once.

One agent interface

A single remote MCP server on the current spec. Agents sign in per user through OAuth and get exactly that person's permissions.

Two ways data comes in

Documents go through staging and human verification. Records from authoritative systems (QuickBooks, Belfry) sync directly with source IDs; only mismatches go to review.

Core works with no AI keys

Records, workflows, MCP tools, keyword search and open-source OCR need no model provider. Semantic search, cloud OCR and in-app Ask switch on with a key and fall back cleanly.

Vercel coordinates, Google Cloud executes

Vercel Workflow tracks multi-step processes and human waits. All heavy or long-running work runs in Cloud Run services and jobs.

Workflows only where work waits

Use a durable workflow when a process pauses for a person or an outside system. Everything else is a direct service call or a scheduled job.

Metrics defined once

Each KPI has one definition. Operational metrics run in Postgres; historical models in Dataform use the same definitions and must reconcile.

Internal users only

Only L&P staff and their agents sign in. Buyers, prospects, clients and competitors are records. No outside portals.

D1Google Cloud is the compute and analytics cloud. Cloud Run services & jobs, BigQuery, Dataform, Artifact Registry, Secret Manager.Your choice. D3Vercel → GCP calls use Workload Identity Federation.Short-lived OIDC tokens instead of stored keys or shared secrets.Workload identity pool for Vercel; one service account per Cloud Run service; Secret Manager for third-party keys.
D4Sales and client success are internal modules. Contacts and prospects are records; no outside logins.Required by Features 04–06; "internal users only" keeps the security model simple.Sales and Clients domains with their own tables and services.
D5One MCP server on the official TypeScript SDK, spec 2026-07-28. No parallel REST "actions" API for agents.ChatGPT and Claude both connect to remote MCP; two agent surfaces drift apart.Tool registry that wraps domain services; read-only annotations on read tools.
D6Agents sign in per user with OAuth 2.1 via Supabase Auth.The MCP spec expects OAuth for remote servers; Supabase supports it with dynamic client registration.Enable Supabase OAuth server; build a consent page; tokens map to the same roles as the UI.
D7Write approvals = client confirmation + server permissions. Human-only gates (verify, final price, submit) are role permissions.ChatGPT and Claude ask the user before any tool not marked read-only; the server enforces who may do what.Permission checks inside each domain service, not in the tool layer.
D8Core runs with no model keys; AI features fall back.Meets the "independent of provider APIs" requirement without losing AI features.Open-source OCR by default; full-text search when embeddings are off; agents reason through MCP.
D9Connectors sync authoritative system data directly, separate from the document pipeline.QuickBooks already owns invoices; re-verifying each row by hand adds nothing.Cloud Run Job per connector; synced tables with source ID, sync log, reconciliation exceptions.
D10Work management is a platform service (tasks, checkpoints, handoffs).Lets a person or a different agent resume work without chat history (Features F3, 09).Work tables + MCP tools to create tasks, save checkpoints and list next actions.
D11Single organization (L&P), with org-scoped data model.Org-scoped RLS also powers per-user agent permissions and keeps a later multi-company option open.organization_id on tenant data; RLS policies on every table.
D12BigQuery holds history and cross-system analysis; Postgres holds live metrics. One set of metric definitions.Postgres serves the app; the warehouse joins bids with accounting and hours over years.Incremental loader with snapshots; Dataform models reconciled against operational totals.
Build order

Phases

Each phase ends with a working result people use, per the delivery rule in Features §10. Parts of the CIP repo can be reused where they fit the design; that is assessed per component.

PHASE 1 · FOUNDATION
  • Vercel, Supabase and GCP projects + Workload Identity Federation (D1–D3)
  • Auth, roles, RLS, audit (D11)
  • Vault, staging, verification pipeline on Cloud Run
  • Correct pricing classification and paid vs billable hours

Done when: a real RFP goes from upload to verified facts.

PHASE 2 · ONE COMPLETE BID
  • Compliance matrix → staffing & pricing → authoring → DOCX/Docs export
  • Proposal review workflow
  • Work management (D10)

Done when: a saved review package with a real blocker list.

PHASE 3 · AGENTS
  • MCP server + OAuth (D5–D7)
  • Read and write tools for every phase 1–2 workflow
  • Test ChatGPT and Claude: read → write → resume

Done when: both agents finish and resume the same task.

PHASE 4 · REVENUE DATA
  • QuickBooks + Belfry connector jobs (D9)
  • Contract administration & billing reconciliation
  • Renewal and PO workflows

Done when: a contract shows hours, cost, invoiced and paid by period.

PHASE 5 · GROWTH
  • Sales & prospecting + Apollo connector (D4)
  • Client success module
  • Signal alerts in the daily digest

Done when: sales works a scored lead list in the app.

PHASE 6 · WAREHOUSE
  • Loader → BigQuery with snapshots (D12)
  • Dataform models from shared metric definitions
  • Win-rate, pricing and contract economics history

Done when: warehouse totals reconcile with the app's.
