L&P Platform Architecture

One design where every piece has a single job and a single owner. It starts from what is already built (repo commit aa4512f), keeps what works, and marks exactly what to change or add so the parts fit together.

What you are building

Category and name

Standard description

An internal business development (BD) lifecycle platform for a security services contractor: capture, proposal and pricing management; win/loss and competitive intelligence; sales prospecting; and contract administration after award.

Technically: a modular monolith web app on Vercel; one system of record on Supabase; a Python worker service for heavy document and web work; a human-verified document pipeline; connectors to business systems; and one remote MCP server so ChatGPT and Claude use the same tools and permissions as staff.

Design rules

Nine rules that keep the pieces consistent

Each rule settles a question that had two answers in the sheet, the old diagram or the repo. Agents and developers check new work against these.

One system of record

Supabase Postgres + Storage hold the authoritative data. Drive, Docs, Sheets, BigQuery and connected systems are sources or copies, never a second truth.

One business-logic layer

The UI, MCP tools, crons and workflows all call the same TypeScript domain services. No rule is written twice.

One agent interface

A single remote MCP server, current spec, signed in per user through Supabase OAuth. Agents get the same role permissions and row-level security as that person.

Two ways data comes in

Documents go through staging and human verification. Records from authoritative systems (QuickBooks, Belfry) sync directly with source IDs; only mismatches go to a review queue.

Core works with no AI keys

Records, workflows, MCP tools, keyword search and local OCR need no model provider. Semantic search, cloud OCR and in-app Ask are add-ons that switch on with a key and fall back cleanly.

Workflows only where work waits

Use a durable workflow when a process pauses for a person or an outside system. Everything else is a plain service call or a scheduled job.

One worker host

Heavy Python work (parsing, OCR, crawling, solvers) runs on one Fly.io app. Light API syncs run on Vercel.

Metrics defined once

Each KPI has one definition in a metrics registry. It runs on Postgres now, and the warehouse reuses the same definitions later.

Internal users only

Only L&P staff (and their agents) sign in. Buyers, prospects, clients and competitors are records, so sales and client data are in scope, and portals are not.

Build order

Getting from today to the target

Each phase ends with something working that people use, matching the delivery rule in your Features §10.

PHASE 1 · FOUNDATION FIXES
  • Pricing classification and hours fixes
  • Remove Railway / Cloud Run configs (D5)
  • Local OCR default (D6)
  • Update scope docs (D1, D9)

Done when: one real bid's pricing reconciles by hand.

PHASE 2 · ONE COMPLETE BID
  • Intake → verify → compliance matrix → pricing → DOCX export on a live RFP
  • Proposal review workflow
  • Work management tables (D8)

Done when: a saved review package with a real blocker list.

PHASE 3 · AGENTS
  • MCP on SDK + OAuth (D2–D4)
  • Write tools for intake, drafts, pricing inputs, tasks
  • Test ChatGPT and Claude: read → write → resume

Done when: both agents finish and resume the same task.

PHASE 4 · REVENUE DATA
  • QuickBooks + Belfry connectors (D7)
  • Billing / labor reconciliation
  • Contract PO and renewal workflows

Done when: a contract shows hours, cost, invoiced and paid by period.

PHASE 5 · GROWTH
  • Sales & prospecting module + Apollo connector
  • Client success module
  • Signal alerts in daily digest

Done when: sales works a scored lead list in the app.

PHASE 6 · WAREHOUSE (IF NEEDED)
  • Pipelines → BigQuery (D10)
  • Dataform models from the metrics registry
  • Historical cohort and win-rate analysis

Start when: Postgres queries get slow or need multi-year history.
